# Материал для защиты: от основ к каверзным вопросам

## Что программа делает

Есть папка текстов. Нужно для каждого слова узнать число его появлений во всех файлах. Например «Word0001 WORD0001, word0001!» превращается в три одинаковых ключа word0001 и счётчик 3. Словарь Map хранит пары «ключ → значение»: String → Integer при подсчёте, String → Long в результате. Ключи уникальны; put существующего ключа заменяет значение.

Генератор сначала придумывает вероятности, затем выбирает слова по ним. Перед записью каждого слова увеличивает независимый эталонный массив long[]. Он считает выборы, а не перечитывает текст тем же парсером. Затем меняет регистр и добавляет пунктуацию. Поэтому сравнение проверяет и подсчёт, и нормализацию. Вероятность — теоретический шанс, count — фактическое число; count не обязан равняться probability × число слов.

Вероятности: положительные веса 0.05 + случайное число [0;1), делённые на сумму. Накопленная вероятность — сумма вероятностей от первого слова до текущего. Случайное число [0;1) бинарным поиском попадает в интервал слова; сложность O(log V). Последний предел принудительно 1.0 против округления double. Seed — начальное состояние псевдослучайного генератора, а не сама вероятность.

## Основы Java

Класс — описание типа объектов и их поведения. Объект — экземпляр класса в памяти. `new HashMap<>()` вызывает конструктор и создаёт объект. Конструктор имеет имя класса, не имеет возвращаемого типа; `private TextFiles() {}` запрещает создавать служебный класс снаружи. Если конструктор не написан, компилятор добавляет конструктор без аргументов с доступом класса.

Метод — именованный фрагмент поведения. Аргументы — передаваемые ему значения. `return` возвращает значение и заканчивает метод. `void` означает отсутствие возвращаемого значения. `main(String[] args)` — точка входа; args — массив аргументов командной строки, нумерация с нуля. static позволяет вызвать метод через класс без создания объекта. public — доступ снаружи; private — только из этого класса; final у класса запрещает наследование, у поля запрещает переприсвоение ссылки (не делает объект неизменяемым!).

Интерфейс WordAnalyzer — договор: любой реализующий класс предоставляет analyze с одним форматом входа/выхода. implements — реализация интерфейса. Поэтому Benchmark может одинаково запускать разные классы. Переменная типа интерфейса может ссылаться на объект конкретного класса — полиморфизм. Никакого общего объекта счётчика между разными запусками нет: analyze создаёт новую карту.

`int` — целое 32 бита; `long` — 64 бита; `double` — число с плавающей точкой; boolean — true/false. Integer и Long — объектные оболочки, нужны в обобщённых коллекциях. Упаковка/распаковка преобразует число в объект и обратно. Integer неизменяем: увеличение создаёт/выбирает другое значение, а не меняет старый Integer. `1L` — long, `1` — int. `var` выводит статический тип из правой части, не означает динамический тип.

`Map<String, Integer>` — обобщённый тип (generics): ключи String, значения Integer. `<>` справа выводит типы. List — упорядоченная последовательность, Set — множество уникальных значений. Path — путь, не открытый файл. Files — статические операции с файлами. TreeMap/TreeSet упорядочивают ключи; HashMap не обещает порядок. Равенство Map сравнивает ключи и значения, а не порядок.

Лямбда `word -> counts.merge(...)` описывает действие с параметром word. Consumer<String> принимает строку и ничего не возвращает. Захваченная ссылка counts не переприсваивается, но объект по этой ссылке изменяется. `Math::addExact` — ссылка на метод: `(a,b) -> Math.addExact(a,b)`. Для допустимых значений равно Integer::sum; при переполнении кидает исключение. `key -> new LongAdder()` создаёт счётчик для отсутствующего ключа. `::` — ссылка на метод, `->` — лямбда или ветвь switch (смысл зависит от места).

`for` повторяет действия; for-each перебирает элементы; while повторяется, пока условие true. if выбирает ветвь, else альтернативу. `==` сравнивает примитивные значения или ссылки объектов, equals — содержимое по правилам типа. Для строк нужен equals. `&&`, `||`, `!` — И, ИЛИ, НЕ; `%` — остаток; `++` увеличивает на 1; `+=` прибавляет; `>>> 1` — беззнаковый сдвиг на один бит, здесь вычисляет середину положительных индексов. Индексы массива от 0 до length-1. Операция `errors++ == 0` сравнивает старое значение, затем увеличивает.

Исключение сообщает о нештатном исходе. throw создаёт/выбрасывает исключение; throws объявляет, что метод может его передать вызывающему. try/catch перехватывает, finally выполняется и при ошибке. try-with-resources автоматически закрывает reader/writer/stream/pool. IOException — проверяемое исключение ввода-вывода; RuntimeException — непроверяемое; ExecutionException оборачивает ошибку фоновой задачи. `instanceof IOException io` одновременно проверяет тип и даёт переменную io. Ошибку работника нельзя просто напечатать и вернуть неполный результат как успешный.

## Вся цепочка выполнения

Main читает аргументы → Statistics.load загружает эталон → Analyzers.create выбирает реализацию → включается таймер → analyze находит файлы, читает, нормализует, считает → при необходимости дожидается потоков и собирает результат → таймер останавливается → Statistics.difference проверяет объединение ключей → печатается итог.

TextFiles.list закрывает поток перечисления каталога; фильтрует только text-NNN.txt, сортирует для воспроизводимого распределения. TextFiles.read читает по строкам, не загружает весь корпус в память. Pattern скомпилирован один раз и безопасен для общего использования; Matcher создаётся отдельно на каждую строку. `[\p{L}\p{N}]+` означает одну или больше букв/чисел Unicode; Java требует двойной обратный слеш в строковом литерале. Цифры сохраняются, иначе все word0001/word0002 слились бы в word.

Workers создаёт фиксированный пул из p платформенных потоков, отправляет p задач. Работник k получает индексы k, k+p, k+2p: каждый файл назначен ровно один раз. При 128 файлах и p=64 — по два файла; при p>числа файлов некоторые задачи пустые. Future — обещание результата. submit запускает задачу асинхронно; get ждёт результат. Ожидание первого Future не запрещает другим задачам исполняться параллельно. Все get должны завершиться до чтения общей карты/суммы. Успешный get обеспечивает видимость действий задачи (happens-before). finally останавливает пул и close ждёт работников, чтобы они не влияли на следующий эксперимент.

В безопасных вариантах все используемые карты либо синхронизированы, либо принадлежат одному работнику. Shared HashMap таким свойством не обладает. Локальная карта создаётся внутри Job, а не снаружи, поэтому не общая. Объединение локальных результатов делает вызывающий поток после завершения задач; оно входит в время.

## Семь реализаций и принципиальная разница

| Вариант | Обновление | Почему такой результат |
|---|---|---|
| sequential | HashMap.merge, один поток | Нет одновременной записи |
| hashmap | общий HashMap, get/put | Гонки счётчиков и структуры, намеренно неправильно |
| synchronized-map | merge на обёртке | Вся операция merge под одним монитором |
| concurrent-get-put | CHM, отдельные get/put | Структура цела, составное увеличение неатомарно |
| concurrent-merge | CHM.merge | Атомарное обновление данного ключа |
| long-adder | computeIfAbsent + increment | Потокобезопасное создание и конкурентный счётчик |
| local-maps | отдельный HashMap на задачу | Нет общих записей, итог объединяется последовательно |

Lost update: A читает 10; B читает 10; A записывает 11; B записывает 11. Должно быть 12. Это возможно даже когда get и put по отдельности потокобезопасны. SelfTest принудительно создаёт именно это расписание через CyclicBarrier на CHM и synchronizedMap. Барьер здесь только демонстрация; в измеряемых алгоритмах его нет.

HashMap дополнительно изменяет внутренние узлы, таблицу, size и цепочки/деревья коллизий без требуемой синхронизации. Один поток может не увидеть запись другого, обновления могут потеряться; возможны исключения/повреждения. Случайный успех не доказывает корректность для всех расписаний. Data race — конфликтующие несинхронизированные доступы к памяти, race condition — более широкая логическая зависимость от порядка; get/put на CHM — пример логической гонки при безопасных отдельных методах.

Collections.synchronizedMap оборачивает карту общим монитором. merge в этой обёртке синхронизирован целиком. get/put остаются двумя отдельными критическими секциями. Исправление составного действия — `synchronized (map) { ... }`, но все участники должны соблюдать тот же замок. При обходе synchronizedMap во время изменений нужен synchronized на самой обёртке. У нас преобразование идёт уже после get всех задач, поэтому конкурентных изменений нет.

CHM допускает высокую степень конкурентного доступа; чтения обычно не блокируются, обновления конфликтующих ключей могут конкурировать за внутреннюю синхронизацию. Нельзя обещать «отдельный замок на каждый ключ» или описывать современные CHM как фиксированные сегменты Java 7. Атомарность merge относится к операции данного ключа, не ко всей карте как одной транзакции.

LongAdder распределяет обновления между внутренними ячейками при конкуренции, затем суммирует. Это уменьшает борьбу за одну ячейку, но требует памяти и вычисления суммы. При малой конкуренции выигрыш не обязателен. sum во время обновлений — не атомарный снимок; после завершения всех задач точен. В выражении computeIfAbsent(...).increment() две операции: нельзя называть всё выражение единой атомарной операцией CHM. Здесь это безопасно, потому что счётчики не удаляются и не заменяются, а increment сам потокобезопасен.

## Каверзные вопросы и ответы

**Где создаются потоки?** Workers.run, Executors.newFixedThreadPool; фактически пул создаёт работников при submit. **Где ждём?** future.get, а при очистке pool.close. **Где общая карта?** Переменная counts до Workers.run в четырёх общих вариантах и LongAdderAnalyzer. **Где локальная?** Внутри лямбды Workers.run в LocalMapsAnalyzer. **Где эталон?** Генератор expected[left]++, затем expected-statistics.txt; загрузка Statistics.load.

**Чем поток отличается от процесса?** Процесс имеет своё адресное пространство, потоки процесса разделяют кучу и ресурсы, но имеют собственные стеки выполнения. **Параллельность и конкурентность?** Конкурентность — несколько задач в работе с возможным чередованием; параллельность — одновременное выполнение. Один CPU тоже может исполнять конкурентную программу.

**start против run?** Thread.start создаёт отдельное выполнение, прямой run — обычный вызов в текущем потоке. Здесь используем submit, а не ручной Thread. **Runnable против Callable?** Runnable без результата и checked exceptions; Callable возвращает результат и может бросить Exception; поэтому pool.submit(() -> job.run(part)) подходит для Future<T>.

**synchronized против volatile?** synchronized даёт взаимное исключение и видимость; volatile даёт видимость/порядок доступа к полю, но не делает i++ атомарным и не защищает внутренности HashMap. final ссылки тоже не защищает её объект. **AtomicLong против LongAdder?** AtomicLong удобен для точного атомарного текущего значения и операций CAS; LongAdder для накопления статистики при конкуренции, без атомарного снимка sum.

**Почему не Integer++ в карте?** Получили число, увеличили, записали — три шага. Integer неизменяем. **Можно ли HashMap.merge из нескольких потоков?** Нет, интерфейсный метод merge сам не обещает синхронизации для любой Map; гарантия зависит от реализации. **Можно ли просто заменить Map на CHM?** Структурную гонку устранит, составную get/put — нет.

**Что делают getOrDefault/put/merge/computeIfAbsent?** getOrDefault возвращает значение либо запасное, не добавляет его; put записывает; merge при отсутствии кладёт 1, при наличии вызывает сумматор; computeIfAbsent вычисляет значение для отсутствующего ключа. Если remapping-функция merge вернёт null, ключ удалится. Наш сумматор null не возвращает.

**CHM допускает null?** Ни ключи, ни значения. HashMap допускает null-ключ и null-значения; здесь их нет. **Что такое коллизия?** Разные ключи попали в одну корзину хеш-таблицы. equals отличает ключи; один hashCode не означает равенства. String неизменяем, поэтому удобен как ключ; изменение полей ключа, влияющих на hashCode, ломает поиск.

**Почему Long после Integer?** Это единый формат результата/эталона, не способ исправить прежнее переполнение. Для огромных корпусов надо считать Long во всех вариантах. Math.addExact выдаёт ошибку вместо тихого переполнения у корректных Integer-реализаций.

**Почему не читать expected как текст?** Вход ограничен шаблоном text-*.txt; служебные заголовки и числа не должны считаться словами корпуса. **Вложенные каталоги?** По условному формату генератора файлы лежат в одном каталоге, рекурсивного обхода нет. **Пустой файл?** Даёт 0 слов. Пустой каталог входа — явная ошибка. Последняя строка без перевода? readLine её прочитает. Регистр турецкой локали? Locale.ROOT исключает зависимость от системной локали.

**Почему не хранить все слова в List?** Потоковое чтение экономит память, каждая строка живёт кратковременно. **Почему не parallelStream?** Явный пул позволяет точно задавать p и видеть распределение. **Почему не виртуальные потоки?** Основная конкуренция за счётчики и CPU; больше дешёвых потоков не устраняет узкое место. Здесь учебный фиксированный пул платформенных потоков.

**Почему nanoTime, а не currentTimeMillis?** nanoTime предназначен для интервалов, не для календарного времени. Наносекунды в единицах не обещают наносекундной точности. Делитель double исключает целочисленное усечение. **Что входит в таймер?** Весь analyze: чтение, разбор, пул, подсчёт, объединение, преобразование; сравнение и вывод снаружи.

**Зачем прогрев?** Загрузка классов/JIT и файловый кэш меняют первые запуски. Прогрев уменьшает начальные эффекты, не гарантирует полной стабилизации. **Зачем медиана?** Меньше влияние одиночного выброса; при 3 измерениях это среднее по порядку, не арифметическое среднее. Сырые значения сохранены, прогревы помечены отдельно. **Почему три корпуса?** Показывают, когда полезная работа начинает покрывать накладные расходы.

**Почему ускорение может быть меньше 1?** Параллельный вариант медленнее последовательного. **Может ли эффективность быть больше 100%?** Иногда из-за кэшей/шума или разных накладных расходов; это повод проверить методику, не автоматическая ошибка формулы. **Какой T1?** Медиана отдельной SequentialAnalyzer для того же корпуса, а не однопоточный запуск CHM. **Почему не строить ускорение ошибочных вариантов?** Быстрый неверный ответ не решает задачу; их времена есть в таблице, но не на графиках корректных алгоритмов.

**Почему мало выигрыша после определённого p?** Мониторы/коллизии, последовательная часть, создание потоков, переключения контекста, пропускная способность памяти/диска, GC. Закон Амдала: S(p) ≤ 1/(f + (1-f)/p) при доле последовательной работы f и идеальных прочих условиях. Это объяснение возможных причин, не доказательство конкретной аппаратной причины без профилирования.

**Можно ли sum проверять до Future.get?** Нельзя считать такой результат финальным. **get в цикле сериализует работу?** Только ожидание результатов, сами задачи уже отправлены все. **Где критическая секция?** Внутри synchronizedMap.merge и внутренних операций CHM; в исходном коде merge может скрывать синхронизацию библиотеки. **Почему ожидание не исправляет HashMap?** Оно делает завершённые действия видимыми, но не восстанавливает потерянные обновления.

**Local maps всегда быстрее?** Нет: O(p×V) памяти для карт и последовательное объединение, создание задач; при большом словаре или малом корпусе расходы заметны. **Сложность?** При ожидаемом O(1) доступа к хеш-таблице подсчёт O(N), локальное слияние до O(pV), чтение O(число символов); бинарный поиск генератора O(log V) на слово. Regex/нормализация тоже потребляют время.

## Рассказ на одну минуту

«Я генерирую корпус с различными регистрами и пунктуацией, одновременно независимо считаю эталон. Все алгоритмы читают одни и те же файлы и одинаково выделяют слова. Есть последовательная версия и шесть многопоточных. Общий HashMap небезопасен; ConcurrentHashMap с get/put защищает структуру, но теряет увеличения. synchronizedMap.merge и CHM.merge корректно обновляют счётчики. LongAdder уменьшает конкуренцию за часто обновляемые значения. Локальные карты убирают общие записи и объединяются после завершения задач. Для каждого числа потоков я делаю два прогрева и три измерения, проверяю весь словарь, беру медиану и считаю ускорение относительно последовательной версии. Конкретный победитель и оптимальное число потоков указаны в таблицах, а не выбраны заранее».
